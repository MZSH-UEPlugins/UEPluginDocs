## 2. 此前验证方向为什么不成立

此前场景以“达到 100+ 节点”为先，导致结构服务于截图数量，而不是服务于业务语义：

1. 大量数据从 Function Entry 参数跨屏扇出，形成不符合正常维护习惯的长线。
2. Branch、For Loop、For Each、Switch 等节点有展示性使用，但没有都构成完整、可解释的执行阶段。
3. “所有节点都有一条线”只能消除孤立节点，不能证明节点对最终结果或副作用有贡献。
4. 编译成功只证明图的类型和语法成立，不能证明路径在运行时被执行、输出正确或修改前后语义受控。
5. 无节点重叠只证明布局几何成立，不能替代业务正确性、可读性和回归验证。
6. 截图主要展示图面，没有同时给出函数调用结果，因此无法从证据判断业务是否真实运行。

## 3. 新测试资产的业务设计门槛

搭图前必须先提交一页场景设计供用户确认。场景至少定义：

- 一句可理解的业务故事，而不是节点类型清单。
- 明确的函数输入、输出和允许的副作用。
- 3 个以上确定性测试用例，覆盖不同的 Branch、Loop 和 Switch 路径。
- 每个测试用例的固定输入、期望输出和不变量。
- 准备修改的一个具体业务规则，以及哪些行为必须保持不变。

推荐下一次使用“订单/批次结算与风险评估”一类可解释场景，例如：遍历项目、按类型 Switch 计算基础值、使用 Branch 应用资格规则、用 For Loop 处理分段奖励、汇总税费/折扣/风险标记，最终返回可核对的结果结构。场景可以不同，但不能为了包含某种节点而添加无意义步骤。

100 个节点只是压力规模，不是成功条件。若自然、可运行的实现不足 100 个节点，应通过真实业务阶段增加合理复杂度，不能复制装饰节点、无效分支或不参与结果的算术链凑数。

## 4. 图结构硬门槛

- 每个 impure node 必须从 Function Entry 的 Exec Pin 可达。
- 每条终止执行路径必须到达 Function Result，或产生场景设计中明确声明的副作用。
- 每个 pure node 的结果必须最终进入条件、赋值、副作用或函数返回；仅连接到另一个无用途节点不算有效贡献。
- Branch 的 True/False、Switch 的业务相关 Case、Loop 的 Body/Completed 必须按场景形成可解释路径；允许空路径时必须在设计中说明原因。
- 修改点的上游来源、下游消费者和终止结果必须在局部视图中同时可见或可连续追踪。
- 禁止从 Function Entry 或单个远端 Getter 向全图星形扇出。成员变量、函数参数或已落地的局部值，应在消费区域附近使用合法 Getter。
- 临时计算结果不能通过复制 Getter 改变语义；需要复用时使用合法的 Local Variable Set/Get，或少量、就近、可读的 Reroute。
- 不允许大量跨屏连线仅靠拉远节点解决。应优先缩短数据依赖；布局平移只负责为新增的真实逻辑块腾出空间。
- 新增逻辑必须连接到现有真实上游和下游，不能作为独立展示块放在空白区域。

## 5. 修改与防重叠流程

一次只修改一个真实业务逻辑点：

1. 用 `GetGraphDetail` 读回目标图的节点 GUID、坐标、Pin 和连接。
2. 用 `SearchGraphNodes` 获取合法 SpawnerId；不得手工伪造。
3. 人工审阅完整 Patch JSON 与当前图详情，检查新增块锚点、预期连接和可能平移的有界右侧闭包。`ApplyGraphPatch` 当前没有 patch 级 dry-run 参数；若必须先看精确预览，应把该能力作为独立前置单元实现并验证，不能调用不存在的 `bDryRun`。
4. 若空间不足，优先整体平移必要的、连通的后续逻辑闭包，为新增块让出空间；不得覆盖旧节点。
5. 使用邻近 Getter 或有限 Reroute 缩短连线，但不能改变数据来源和执行语义。
6. 应用后立即读回，核对新增节点、所有连接、旧节点 GUID 和非目标区域坐标。
7. 编译并实际执行测试用例；只有通过后才截图和显式保存。
8. 保存、关闭、重开后再次读回、编译并执行同一组测试。
9. 验证 Undo/回滚能恢复精确基线；若当前工具面不能直接触发某项验证，应明确报告，不能推定通过。

`ApplyGraphPatch` 的布局成功不代表业务成功。只要出现连接缺失、旧逻辑意外变化、运行结果不符、不可读长线或未解决重叠，整个原子修改都不合格。

## 6. 运行时证明

Compile 是运行验证的前置条件，不是终点。每个修改阶段都必须留下结构化证据：

- 修改前实际调用函数，记录全部固定输入、返回值和可观察副作用。
- 修改后对同一输入再次调用，预期变化的用例必须得到新结果。
- 未针对修改的用例及不变量必须保持一致。
- 至少一个用例进入新逻辑的主路径，至少一个进入边界或拒绝路径。
- 保存、关闭、重开后第三次运行同一组用例，结果必须与保存前一致。
- 若场景依赖随机数、时间或外部状态，必须固定种子/输入或替换为确定性测试接口。

结果证据应包含可机器读取的调用输出或属性读回；仅看图、日志中的 Compile Success 或节点计数均不算运行时证明。

当前 53 个 MCPBlueprint 工具没有通用的“调用任意 Blueprint 函数”工具。下一任务必须在搭建 100+ 节点前先选定并验证一个隔离运行入口，例如：自动化测试直接调用生成类、专用 Caller Blueprint 通过可控事件执行，或隔离测试地图中的 PIE harness。运行入口、触发方式和结果读回方式必须写入场景设计；如果入口本身尚不可用，应先把它作为独立前置能力完成，不能用 Compile Success 代替执行。

## 7. 截图交付规范

下次任务至少交付以下真实 UE 编辑器截图，并按修改步骤编号：

1. **修改前全图**：能看清业务阶段、主 Exec 流向和整体组织，不以缩放到文字不可读为代价追求全景。
2. **修改前局部**：待修改逻辑及其上游、下游连接清晰可见。
3. **每次修改后的同画幅局部图**：一次原子修改一张；与上一张保持相同区域和近似缩放，便于直接对比。
4. **修改后全图**：证明非目标阶段仍在原位，且没有新增大范围长线或重叠。
5. **运行结果图**：展示固定输入和可核对输出/副作用，证明函数确实被调用。
6. **保存重开图**：重开后同一局部画面，节点、Pin、连接和位置均清晰可见。
7. **Undo/恢复图**：适用时展示恢复后的同画幅局部结果，并附结构读回证据。

“修改前 / 修改后”只用于实际的局部业务逻辑变化：新增、删除或替换节点，修改 Pin 默认值，或改变连线关系。单纯执行自动布局、移动节点、降低交叉线、调整截图画幅或添加 Comment Box，都不能标成逻辑 Before/After。修改后图中的 Comment Box 只包围本次实际变化的节点；修改前后必须使用同一目标节点、相同分辨率和相同缩放，并同时展示该局部的上游与下游。

截图必须来自真实 Blueprint Graph 控件，能看见节点本体、Pin 和连线；禁止 wires-only、拼接伪 UI、孤立节点阵列或只展示节点数量。应清理无关窗口和敏感路径，确保标题、Pin 名称和关键数值可读。原始截图可先归档到 AIHub 项目产出，确认合格后再选择适合公开的版本进入仓库文档。

## 8. 直接否决条件

出现任一项即不得宣称验收完成：

- 为满足 100+ 数量添加装饰节点、重复链或无效分支。
- Flow Control 节点没有进入从 Entry 可达的真实 Exec 链。
- pure node 不贡献给最终返回、条件、赋值或副作用。
- 只有编译成功，没有实际调用与结果核对。
- 只有零孤立或零重叠，没有业务语义证明。
- 节点很多但有效连接很少，或大量节点只是并排展示。
- 存在可由邻近 Getter/Set-Get/Reroute 消除的跨屏长线。
- 新增逻辑覆盖旧节点，或为了腾空间无界移动整图。
- 截图文字不可读、只显示线，或修改前后不是可比较画幅。
- 在人工构造的布局压力图上证明局部改善后，将其表述成真实项目验收。
